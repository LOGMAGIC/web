# Gopher 协议在 SSRF 中的作用与使用场景

> gopher://host:port/_ 后面跟的所有数据会被原样发到目标端口——相当于借 SSRF 服务器之手，替你向内网任意端口开一条 TCP 连接、塞任意字节进去。所以它不只是“协议”，而是**任意协议伪造器**。

## 什么时候需要 Gopher

核心判断：当目标服务不是"发一个 GET 就能拿结果"，而是需要**对话**（发多条命令/带 body 的请求/协议握手）时，就轮到 gopher。

| 场景                 | 为什么必须 gopher                                            |
| -------------------- | ------------------------------------------------------------ |
| 打 Redis 写 webshell | 要按顺序发 set → config set dir → config set dbfilename → save 一整套多行命令，http/dict 都做不到多行交互 |
| 打无密码 MySQL       | 要伪造 MySQL 客户端握手包、认证包，纯二进制协议对话，只有 gopher 能塞进去（Gopherus 直接生成） |
| 打 FastCGI (9000)    | 伪造 FastCGI 协议包，让 php-fpm 执行任意 PHP 代码，直接 RCE，绕过 disable_functions 也常用这招 |
| 伪造 POST 请求       | SSRF 只能 GET（如 http:// 包装器），但内网接口要 POST + 自定义头 + body → 用 gopher 构造完整 HTTP 请求打过去 |
| 打 SMTP (25)         | 伪造 HELO/MAIL FROM/DATA 整个发信过程，从内网邮件服务器发钓鱼信、VRFY 枚举用户 |
| 打 Memcached (11211) | 写入伪造数据污染 session/缓存                                |

## 四种协议分工（SSRF 标准套路）

- `file://` → 读本地文件（只读，不联网）
- `dict://` → 探测：端口扫描、探测服务版本（`dict://ip:port/info` 一行命令）
- `http://` → 访问内网 web 服务、云元数据（169.254.169.254）
- `gopher://` → 真正的攻击：伪造协议对话、写文件、执行命令

> 记忆口诀：dict 是探路的，gopher 是下手的。 示例：先用 `dict://.../info` 确认 Redis 存活 → 切换 gopher 发送完整攻击序列。

## 两个前提（不然 payload 再对也没用）

1. **后端得支持 gopher**：PHP 的 curl 支持；`file_get_contents()` 不支持 gopher（只支持 http/https/ftp/file）；Python requests 只认 http/https。遇到 SSRF 先摸清后端用什么发起请求。
2. **注意编码次数**：数据经过 `$_GET` 会解码一次，payload 里若有 `%0d%0a` 可能需要二次编码。

# gopherus的使用

Gopherus的使用非常直观，基本命令格式如下：

```bash
gopherus --exploit [服务类型]
```

例如，要利用Redis服务的SSRF漏洞，只需运行：

```bash
gopherus --exploit redis
```

然后根据工具提示输入必要的参数，如**目标IP、端口、命令**等，工具会自动生成相应的gopher链接。
